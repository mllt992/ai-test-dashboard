# Database prerequisites and rollout

These are reviewed source migrations, not a production deployment. Apply them in numbered order only after a database owner verifies the existing schema, tenant routing, RLS policies, role permissions and any existing triggers in a disposable copy or staging database. No credentials, grants, RLS policies or production settings are changed here.

The repository did not contain a schema export. The supported prerequisite is the tables and columns already read/written by `functions/handler.mjs`, with UUID primary/reference IDs, timestamp `created_at`/`updated_at` columns and text statuses. `test_runs`/`test_cases` require `project_id` and nullable `plan_id`; screenshots must be a JSON-compatible array column. Additional required columns without defaults need an explicit adaptation. The tests create this minimal contract, not a claimed copy of the production schema. Inspect actual column types and existing triggers before applying; migration failure must roll back, never be worked around by disabling security.

`001_business_consistency.sql` adds error logs, a current-result pointer, run completion time, transaction-safe triggers and three invoker RPCs. Result status is the latest `created_at` execution timestamp, then UUID descending for equal timestamps. APIs accept optional ISO `executedAt`; otherwise server submission time is used. A late older result is retained without reverting current state. Locks serialize submissions for a case and state changes for a defect. Case status and its result pointer cannot be manually overwritten. All history fields are immutable except screenshots. Deleting a result recomputes current status when its parent case exists. A missing parent skips synchronization only if PostgreSQL's `row_security_active` confirms the current invoker has unfiltered case visibility; no security policy is bypassed. Under active RLS an absent and a hidden case cannot be distinguished, so deletion fails and rolls back. This also means case/project cascading deletion may be blocked for an RLS-limited invoker, even when the parent really has gone. Verify the runtime role and actual FK cascade behavior during schema-owner rollout review; orphan maintenance under active RLS requires a separately reviewed authority, which this migration does not grant. Existing result history is backfilled; historical defect states and run completion times are not guessed.

Result deletion has a second RLS requirement: deleting a non-current historical result leaves the case status and current-result pointer unchanged. Deleting the current result can recompute only when `row_security_active(test_results)` is false for the invoker; otherwise the operation is rejected and rolled back because filtered history cannot establish the true next result. This remains conservative even for an active policy that appears to allow all rows. The runtime role, full-history visibility and cascade behavior must be verified during rollout rather than widened by this migration.

Adding a solution is allowed from open/in_progress/reopened and sets fixed. A retest is allowed only from fixed: passed sets verified, failed sets reopened. Manual transitions allow open/reopened to in_progress/fixed, in_progress to fixed, verified to closed; fixed to verified/reopened requires a retest. All record/state writes commit or roll back together. Run creation requires running; explicit running to completed stamps `finished_at`; later edits preserve that timestamp and reopening is rejected.

Error logs preserve text exactly and permit at most 65,536 Unicode code points (`Array.from` in JS, `char_length` in PostgreSQL). Over-limit API requests receive HTTP 413 without writing. RPC absence or database errors return safe failures with no sequential-write fallback. Existing legacy invalid rows are not erased: new CHECK constraints use `NOT VALID`, enforce new writes, and should be validated by the database owner after auditing existing data.

These migrations intentionally do not repair authentication. Do not publish this anonymous adapter as a protected multi-user service until issue #1's identity provider and permission model are decided and implemented.
